# 迭代需求澄清与验收边界

## 1. 已确认要求

- 部署目标是 Vercel Web 应用。Tauri、Docker 多平台发布和桌面安装包不属于当前迭代验收范围。
- Node 26、Next 16.4.5、React 19.3.1 是当前工程基线；后续依赖升级必须以 Vercel 构建和运行结果为准。
- GitHub Actions 是必需质量门禁：普通 PR、`main` push 和手动触发都要执行 lint、TypeScript、Jest 和 Vercel 构建；质量通过后才允许部署。
- 现有功能必须保持：首次输入访问码、自定义接口与自定义模型分离、后端模型名与展示名映射、图片上传/状态/预览/双击查看/底层传输。
- Claude 已完成的 UI 改动视为当前交互基线。后续工程优化应围绕现有 UI 行为验证，不直接重做视觉方案。
- 允许直接修改代码；但凡涉及用户可见行为、交互流程、Provider payload、部署方式或验收指标，必须先确认需求，再进入实现阶段。
- 迭代按阶段集中修改；每阶段完成实现、验证、更新计划文档后一次提交 Git。除明确要求外，不自动推送远程。

## 2. 当前优化目标

优先改善用户可感知的速度和稳定性：首屏可交互、聊天输入响应、首 token 延迟、流式输出平滑度、长对话滚动、图片预览和移动端操作。性能改动不能改变 Provider payload、SSE 停止/错误恢复、授权阻止发送或图片资源所有权。

## 3. 已完成与未完成

- 已完成 Node 26/Next 16 基线升级、Vercel-only CI/CD、图片生命周期与双击交互、流式更新批处理、首页精确 store selector、空闲资源加载、Markdown 插件按需加载和流式持久化抑制。
- 仍需建立 Vercel preview 的真实 Web Vitals、首屏网络瀑布、长消息滚动和图片交互基线；当前 Docker 构建和 Jest 结果不能替代浏览器数据。
- 仍需根据真实指标决定是否拆分非持久化 streaming store、继续拆分聊天模块、优化图片布局和处理 Edge runtime/`preferredRegion` 弃用提示。

## 4. 当前不应扩大的范围

不因性能优化引入新的 Provider 协议、改变默认模型语义、重做授权流程、替换 Vercel 部署方式或同时升级多个高风险主版本。每项优化都要有指标、测试或构建产物作为依据。

## 5. 后续阶段验收模板

每阶段记录：优化前指标、改动文件和行为影响、Node 26 Docker 验证、GitHub CI 结果、Vercel preview 浏览器结果、已知限制和提交号。若没有真实浏览器数据，只能标记为“构建/单元验证完成”，不能宣称用户体验已经改善。

## 6. 待确认选项

代码实现可以继续，但下列需求确认前，不改变对应边界：

1. 性能基准设备：默认采用桌面 Chrome 加一台低端 Android 移动设备，还是只采用桌面浏览器？
2. Vercel 部署：继续使用当前 GitHub Actions 的 Vercel CLI，还是改由 Vercel Git Integration 负责部署、Actions 只做质量门禁？
3. 优化边界：是否坚持只做保持行为的性能优化；涉及交互变化时，先补充需求和验收项？
