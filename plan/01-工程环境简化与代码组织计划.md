# 工程环境简化与代码组织计划

## 1. 当前基线

项目采用 Next.js 14、React 18、TypeScript 和 Yarn，网页端代码集中在 `app/`，测试位于 `test/`，构建辅助脚本位于 `scripts/`，桌面端位于 `src-tauri/`。现有重构已经拆出 `app/client/platforms/base.ts`、`app/utils/model-detection.ts`、`app/store/chat-actions.ts` 等模块，但聊天主流程仍跨越组件、Store、平台客户端和工具函数。

后续简化应优先处理这些边界：

| 区域 | 当前问题 | 目标 |
| --- | --- | --- |
| 聊天编排 | `components/chat.tsx`、`store/chat-actions.ts` 共同承载输入、会话、请求和响应状态 | 组件只负责交互，Store 只负责状态，编排逻辑进入独立 service |
| 平台客户端 | `openai.ts` 同时处理模型判断、URL、普通聊天、图片生成、图片编辑和响应解析 | 统一请求管线，按能力和协议拆分 adapter |
| 工具函数 | `utils/chat.ts` 同时包含图片、缓存、SSE 和上传逻辑 | 拆为 `media`、`transport`、`cache` 三个职责域，并保留兼容导出 |
| 配置与常量 | `constant.ts` 混合路由、模型、Provider 和 UI 默认值 | 按 `routing`、`models`、`features`、`ui` 分组，逐步迁移调用方 |
| 工程脚本 | Node 版本检查、mask 构建、Next/Tauri 构建入口分散 | 统一脚本入口和失败信息，确保本地与 CI 使用同一命令 |

## 2. 目标结构

建议新增以下边界，先迁移新代码，再逐步移动旧实现：

```text
app/
  domain/model/        # 模型标识、能力和限制
  domain/message/      # 消息与多模态内容规范化
  services/chat/       # 请求编排、重试、流式生命周期
  services/media/      # 图片上传、压缩、缓存、Blob 转换
  client/platforms/    # Provider adapter，只保留协议差异
  components/chat/     # 输入、消息、操作栏等展示组件
```

所有跨边界数据使用明确 TypeScript 类型，禁止以 `any` 作为 adapter 的长期接口。旧路径可通过 barrel re-export 保持兼容，避免一次性修改大量消费者。

## 4. 验收标准与风险

每次拆分都必须保持现有测试通过，并至少增加一条针对新边界的测试。服务层迁移完成后，同一请求在 Web、Tauri、直连 Provider 和统一代理下应产生一致的规范化消息。主要风险是循环依赖、旧会话数据迁移和流式响应行为变化，因此应采用小提交、barrel 兼容层和真实 SSE fixture 逐步迁移。
