# 工程代码与性能优化分析报告

## 1. 范围与结论

本报告以 Vercel 部署的 Web 应用为唯一目标，暂不评估 Tauri、Docker 多平台发布和桌面包。当前功能升级已经具备稳定基线：Node 26、Next 16.4.5、React 19.3.1，GitHub Actions 已执行 lint、TypeScript、Jest 和 Vercel 构建门禁。

当前主要性能风险集中在客户端状态更新和首屏依赖加载，而不是 API route 数量。优先优化聊天流式渲染、持久化写入、Markdown 解析和全局 store 订阅，再处理 bundle 和图片细节。优化前先补齐可重复的构建、运行时和浏览器指标，避免凭感觉改动。

## 2. 现状盘点

- `app/` 共 279 个文件、约 1.9 MB；最大模块包括 `chat.tsx`（约 30.6 KB）、`openai.ts`（约 27.3 KB）、`chat-actions.ts`（约 22.8 KB）和 `markdown.tsx`（约 13.3 KB）。
- `home.tsx` 已对主要页面做动态加载，但同时订阅完整 `useAppConfig`，并在应用挂载时预加载 Google Font、tiktoken、模型列表和 MCP 初始化。
- `Chat`、`ChatActions`、`Markdown` 等组件仍有完整 store 订阅；流式回复每次更新都会克隆 `session.messages`，触发聊天树、侧栏和持久化层重新检查。
- `createPersistStore` 将状态序列化到 IndexedDB，虽然写入有 300 ms debounce，但聊天流式更新、工具事件和输入状态仍共享同一持久化模型。
- `Markdown` 同时引入 GFM、数学、KaTeX、高亮和 Mermaid 能力；Mermaid 已延迟加载，其余解析依赖仍可能进入聊天相关 bundle。
- Vercel 构建已经稳定，但仍有 Edge runtime 和 `preferredRegion` 弃用提示；当前没有 Lighthouse、Web Vitals、bundle 体积或长消息压力基线。

## 3. 分阶段优化方案

### P0：建立基线

记录 Vercel build 时间、首屏 JS 体积、首屏加载、聊天输入响应、首 token 延迟、流式更新频率和 100/500 条消息下的滚动帧率。启用 `ANALYZE=true` 生成 bundle 报告，增加浏览器 smoke 测试和可选的 Lighthouse CI，不把网络波动造成的指标直接作为失败条件。

### P1：降低聊天更新成本

把 `useChatStore()` 的完整订阅改为字段 selector；拆分聊天输入、消息列表、消息行和侧栏的更新边界。流式文本更新通过 `requestAnimationFrame` 或固定节流批处理，持久化只在消息稳定、会话切换或窗口离开时写入。保持现有 SSE、停止请求和错误恢复行为不变。

### P2：优化首屏与 bundle

将 Markdown 的 KaTeX、highlight、Mermaid 和导出能力按实际内容懒加载；模型列表、tiktoken、MCP 和字体加载改为空闲或功能触发时执行。检查 `react-router-dom`、`lodash-es`、图表和实时音频依赖是否重复进入首屏，使用 Vercel 构建产物确认收益。

### P3：图片与交互性能

为上传预览增加尺寸、解码和缩略图策略，避免大图同时参与布局；统一 Blob URL 回收和缓存资源释放。长消息、连续粘贴、多图预览、移动端键盘和双击查看纳入浏览器回归。

### P4：持续验证与 Git 记录

每个阶段集中修改后运行 `yarn lint`、TypeScript、`yarn test:ci` 和 `yarn vercel-build`，再执行受影响的浏览器 smoke/性能检查。更新本报告的阶段记录后一次提交 Git；GitHub Actions 继续作为 PR 和 `main` 的必需质量门禁。

## 4. 验收指标与边界

首屏和聊天性能指标必须记录优化前后数据；长消息列表滚动不得出现持续长任务，流式输出不能明显增加首 token 延迟。构建体积和依赖懒加载以 Vercel 产物为准。真实 Provider 网络、低端设备和浏览器扩展造成的差异单独记录，不通过改变业务协议掩盖。
