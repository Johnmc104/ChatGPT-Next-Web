# 自定义模型与名称映射计划

## 1. 功能边界

“自定义模型”只描述模型是什么以及如何在界面展示：模型 ID、Provider、展示名、能力、上下文和启用状态。它与“自定义接口”分离：同一个模型可通过多个接口使用，同一个接口也可暴露多个模型。

## 2. 名称不一致问题

内置模型使用 `provider/model` 形式，例如 `openai/gpt-4o-mini`；后端 `DEFAULT_MODEL`、`CUSTOM_MODELS` 或设置 URL 可能传入 `gpt-4o-mini`、部署名、别名或带 Provider 后缀的值。当前 `getModelProvider()`、`collectModelTable()` 和 `modelConfig` 选择值分别处理这些格式，容易出现“列表显示一个名字、请求发送另一个名字、默认模型无法选中”的问题。

## 3. 统一模型记录

定义独立的模型记录：

```ts
interface ModelRecord {
  id: string;              // 发送给上游的模型 ID
  displayName: string;     // UI 展示名
  providerId: string;      // 逻辑 Provider
  endpointId?: string;     // 使用的自定义接口
  deploymentName?: string; // Azure 等部署名
  capabilities: ModelCapabilityProfile;
  available: boolean;
  source: "builtin" | "server" | "custom";
}
```

解析顺序固定为：完整 `id@provider` → Provider + model ID → server alias → 内置模型 ID → 自定义模型。UI 始终保存 `id` 和 `providerId`，只把 `displayName` 用于显示；请求 adapter 负责把 `id` 映射为 Azure deployment 或接口所需名称。

## 4. 实施阶段

- **M-Model-1**：新增模型记录和别名解析函数，覆盖 `DEFAULT_MODEL`、`CUSTOM_MODELS`、URL payload 和旧持久化值。首轮已完成 `resolveModelSelection()`，可处理 `provider/model`、`model@Provider` 和未知自定义 ID。
- **M-Model-2**：自定义模型编辑器支持 ID、展示名、Provider、能力标签和启用开关；输入重复 ID 时给出冲突提示。首轮已将 `CUSTOM_MODELS` 解析和重复/空展示名校验抽出，并接入设置输入框。
- **M-Model-3**：模型选择器按 Provider 分组，显示来源和能力；当前选中的模型即使后端列表变化也保留并标记不可用。首轮已保留不可用的当前模型、增加不可用提示，并修复 Provider 列表随选择变化的同步。
- **M-Model-4**：请求、摘要、图片和工具调用统一使用 canonical ID；增加模型列表快照和别名回归测试。首轮已在聊天请求前 canonicalize 并持久化模型 ID，后续摘要/图片路径复用该值。

## 5. 验收标准与进度

后端设置 URL 传入的模型名与内置名称不一致时，仍能正确选中、显示和发送；同名不同 Provider 不互相覆盖；旧配置可迁移；未知模型不会被静默替换。
