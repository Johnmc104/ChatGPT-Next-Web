# 新模型兼容与图像解析计划

## 1. 现状与问题界定

当前模型列表来自 `app/constant.ts`，能力判断由 `app/hooks/useModelInfo.ts` 的缓存、`app/utils/model-detection.ts` 的字符串规则和 `VISION_MODELS` 配置共同决定。普通视觉请求在 `app/client/platforms/openai.ts` 中统一为 OpenAI `messages[].content` 格式，再由 `preProcessImageContent()` 将 Service Worker 缓存 URL 转成 base64。图像生成和编辑分别走 `/api/image-gen`、`/api/image-edit`，后者使用 multipart/form-data。

当前最多只能选择三张图片，原因是 `app/components/chat-images.ts` 的 `MAX_ATTACH_IMAGES = 3`，同时上传和粘贴入口都按该值截断。这是产品输入限制，不代表所有模型的真实上限；不同 Provider 可能支持不同数量、尺寸、格式和单张大小。现有消息类型只声明 `text` 与 `image_url`，对 Gemini `inlineData`、Anthropic `source` 等格式没有显式适配层。

## 2. 兼容目标

建立一个以能力为中心的模型协议，至少包含：

```ts
interface ModelCapability {
  textInput: boolean;
  imageInput: boolean;
  imageOutput: boolean;
  imageEdit: boolean;
  streaming: boolean;
  tools: boolean;
  maxInputImages?: number;
  acceptedImageTypes?: string[];
  maxImageBytes?: number;
}
```

模型名称只用于展示和 fallback，UI 与请求路由优先使用 capability。`/api/model-info` 返回的元数据应覆盖默认模型、`CUSTOM_MODELS` 和动态 Provider 模型；未知模型显示“能力未确认”，允许用户显式声明，而不是默认假设支持视觉。

## 3. 图像解析统一方案

### 输入规范化

新增 `normalizeMultimodalContent()`，把文本、URL、data URI、Blob 缓存 URL 和各 Provider 的图片对象统一为内部 `ImagePart`：

```ts
interface ImagePart {
  kind: "image";
  source: { type: "url" | "base64" | "blob"; value: string };
  mimeType?: string;
}
```

规范化阶段负责 MIME 检查、去重、顺序保持、单张大小和总数量限制；未知字段保留在 `metadata`，避免新模型响应被静默丢弃。Provider adapter 再将 `ImagePart` 转换为 OpenAI `image_url`、Gemini `inlineData` 或 Anthropic `source`。

### 发送路径

1. UI 根据 `imageInput`、`imageEdit` 和 `maxInputImages` 决定是否显示上传入口及上限提示。
2. 上传服务保留原始 Blob 元数据；视觉聊天可按 Provider 要求压缩为 data URI，图像编辑直接发送 Blob。
3. 请求 adapter 根据能力选择 JSON 或 multipart，不在 `openai.ts` 中堆叠模型名称判断。
4. 响应 parser 统一处理 URL、base64、SSE partial image 和错误响应，并将结果写入缓存后再持久化消息。

建议默认上限仍为 3，避免突然增加带宽和上下文成本；后续按模型能力动态设置，允许配置覆盖，且在超限时给出可操作提示。

## 4. 分阶段实施

- **M1：协议与测试**：新增 `ImagePart`、能力字段和规范化函数；覆盖 data URI、缓存 URL、多图、坏 MIME、空内容和未知 Provider 字段。
- **M2：输入上限解耦**：将硬编码常量改为 `resolveMaxInputImages(model)`；修复多次选择时的截断、删除和上传失败回滚。
- **M3：Provider adapter**：先保持 OpenAI 兼容格式，再增加 Gemini/Anthropic 等转换器；统一流式事件和图像生成结果。
- **M4：产品化**：显示模型能力标签、图片数量/大小提示、失败重试和降级到文本的选项；补充端到端 mock。

## 5. 验收标准

至少验证：单图、多图、粘贴、拖拽、HEIC 转换、编辑请求、普通视觉请求、partial image 流和历史消息重放。每种模型能力都应有路由快照测试，确保不支持图片的模型不会发送图片字段，也不会在 UI 中误显示上传按钮。任何 Provider 返回的图片都必须可预览、可刷新、可导出，并在失败时释放 Blob URL 和缓存资源。
